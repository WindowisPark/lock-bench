v3 실험을 통해 얻은 교훈

1. "재시도를 늘리면 성공률이 올라간다"는 반만 맞는 말이다

OPTIMISTIC_LOCK에 retry를 5에서 50으로 10배 늘리니 성공률은 45% → 99.9%로 올라갔다. 하지만 p95가 3초에서 12초로 4배 늘었다. 성공은 하되, 사용자가 기다리다 떠나는 성공이다. 재시도는 "실패를 감추는 도구"이지 "성능을 높이는 도구"가 아니었다.

2. 커넥션 풀을 아무리 분리해도, 진짜 병목이 DB 엔진이면 소용없다

Lock Bleed를 해결하려고 읽기/쓰기 HikariCP 풀을 완전히 분리했다. 결과는 p95가 11.74초에서 11.40초. 3% 개선. 풀은 멀쩡했다 — 문제는 200개 트랜잭션이 같은 row에 SELECT FOR UPDATE를 걸면서 InnoDB lock manager 자체가 느려지는 것이었다. 병목의 위치를 정확히 모르면, 엉뚱한 곳을 최적화하게 된다.

3. 공정(Fair)한 락이 빠른 락보다 결과적으로 더 빠르다

직관적으로 "순서를 안 지키는 놈이 더 빠르지 않나?" 싶었다. 실제로는 정반대였다. Fair Lock이 Unfair보다 p95를 52~71% 줄였다. 이유는 단순하다 — 비공정 락에서는 운 나쁜 스레드가 계속 밀려나면서 tail latency가 폭발한다. 공정 대기열은 "최악의 경우"를 억제해서, 평균도 최악도 함께 좋아진다.

4. PESSIMISTIC_LOCK은 "정합성의 왕"이지만 대가가 크다

MySQL 단독에서 c=200 100% 성공. 데이터 정합성은 완벽하다. 하지만 그 대가로 같은 DB의 읽기 API까지 30초씩 멈춘다 (Lock Bleed). "내 트랜잭션은 안전해"가 "옆 서비스가 죽어"로 번진다. PESSIMISTIC은 동시성이 낮고 트랜잭션이 짧을 때만 써야 한다.

5. Virtual Thread는 만능이 아니다 — DB 커넥션 풀이 좁으면 오히려 역효과

Virtual Thread + PESSIMISTIC_LOCK의 throughput은 PLATFORM의 1/3이었다 (75 vs 221 rps). 200개 VT가 10개 커넥션을 놓고 경쟁하니, 빠른 컨텍스트 스위칭이 오히려 lock contention을 증폭시켰다. Virtual Thread의 이점은 I/O 대기를 잘 양보하는 것인데, DB 커넥션 풀이 좁으면 "양보할 곳"이 없다.

6. 락 전략 선택은 "어떤 락이 좋은가"가 아니라 "어디서 락을 잡을 것인가"이다

결국 가장 큰 차이를 만든 것은 락의 종류가 아니라 락을 잡는 위치였다. DB에서 잡으면 (PESSIMISTIC/OPTIMISTIC) 커넥션이 묶이고, 같은 DB를 쓰는 모든 것이 영향받는다. Redis에서 잡으면 (Redisson) DB 커넥션은 락 획득 후 순간만 쓰고 즉시 반환한다. Redisson Fair Lock + PLATFORM + c≤50이 현 시점 최적 조합인 이유가 여기에 있다.
